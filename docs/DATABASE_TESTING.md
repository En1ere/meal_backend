# Ручная приёмка PostgreSQL Meal Planner

Документ предназначен для проверяемого production-like прогона PostgreSQL 18 на отдельном тестовом стенде. Все изменения данных выполняются только после фиксации baseline и в конце должны быть полностью удалены или восстановлены из проверенной копии.

## 1. Предусловия и журнал запуска

Зафиксируйте в отчёте:

- дату, исполнителя, hostname, версию ОС и `SELECT version()`;
- имя БД и владельца без вывода паролей/connection string;
- commit/revision backend и версию приложения;
- список миграций и checksum manifest;
- размеры БД, схемы `meal`, количество таблиц и baseline-счётчики;
- путь, размер и SHA-256 свежей backup-копии;
- согласованный способ очистки и точку восстановления.

Перед мутациями снимите свежий custom-format backup, выполните `pg_restore --list` и убедитесь, что файл читается. Не используйте существование файла как доказательство возможности восстановления.

## 2. Базовая инфраструктура PostgreSQL

1. PostgreSQL слушает только согласованные интерфейсы; на тестовом VPS production-like вариант — loopback.
2. В `pg_hba.conf` нет `trust` для TCP и широких внешних сетей; парольные подключения используют SCRAM.
3. SSL включён там, где соединение выходит за loopback.
4. `pg_file_settings` не содержит ошибок; последние логи PostgreSQL не показывают crash recovery, corruption или повторяющиеся FATAL.
5. Время БД и ОС синхронизировано; timezone приложения и timestamp-поля интерпретируются однозначно.
6. Есть автоматизированная backup-политика, off-host копия, retention и подтверждённый RPO/RTO. Если этого нет, публичный production-запуск заблокирован.

## 3. Роли и минимальные права

Проверить отдельно owner/migration role и runtime role.

- Runtime-role имеет `USAGE` схемы, но не `CREATE`.
- Runtime-role не владеет схемой/таблицами, не является superuser, не создаёт роли/БД и не имеет replication/bypass RLS.
- `DELETE`, `INSERT`, `UPDATE`, `SELECT`, sequence и function grants совпадают с `db/grants.sql` и manifest.
- Запрещённый `DELETE` на защищённой таблице возвращает permission denied и не меняет строки.
- Разрешённые scheduled/maintenance-операции получают только необходимые права.
- `PUBLIC` не имеет неожиданных прав на schema, tables, sequences или functions.
- Новый объект после миграции получает ожидаемые default privileges.

После проверки перечитайте grants из системного каталога, а не только из migration SQL.

## 4. Миграции

1. На пустой БД выполните `npm run db:plan`, затем `npm run db:migrate`.
2. Сверьте последовательность, количество и SHA-256 всех миграций с manifest.
3. Повторный `db:plan` не предлагает уже применённые шаги.
4. Повторный `db:migrate` идемпотентен и не меняет структуру/справочники.
5. Изменённая уже применённая миграция или неверный checksum останавливает запуск до DDL.
6. Искусственно оборванная миграция откатывает всю транзакцию и не оставляет частично созданные объекты.
7. Миграция не блокирует таблицы дольше согласованного окна; длительные операции и индексы имеют план отката.

Ожидаемый текущий baseline: 31 миграция, 214 таблиц схемы `meal`, 492 внешних ключа; конкретные значения перепроверьте по текущему manifest, а не переносите слепо между версиями.

## 5. Структурная целостность

Проверить системными каталогами:

- все primary/unique/check/foreign-key constraints валидированы;
- все индексы `indisvalid=true` и `indisready=true`;
- внешние ключи имеют ожидаемые `ON DELETE`/`ON UPDATE` действия;
- обязательные tenant/user/family связи не допускают orphan rows;
- enum/check-значения совпадают с API-моделями;
- денежные значения хранятся в minor units/точном числовом типе, без float;
- timestamp-поля имеют timezone там, где это момент времени;
- optimistic version/revision поля изменяются предсказуемо;
- idempotency/audit уникальности не допускают двойной эффект;
- sensitive/provider payload отделён от безопасных проекций.

Для каждой критичной FK выполните одну успешную вставку и одну вставку с несуществующим родителем внутри тестового набора данных.

## 6. Справочники и стартовые данные

На чистом baseline разрешены только канонические системные данные.

1. Единицы измерения: ровно семь актуальных записей с устойчивыми кодами и неизменными ID при повторном seed.
2. Billing products: `free`, `plus`, `pro`, без demo-подписок и пользовательских периодов.
3. Активная AI rule version и recipe policy присутствуют в согласованном количестве.
4. Нет пользователей, семей, рецептов, платежей, сессий и другого доменного demo-контента.
5. Seed конфликтующего стабильного кода с иным ID/смыслом завершает операцию ошибкой и rollback.

## 7. Тестовые персоны и изоляция данных

Создайте уникальный namespace запуска и минимум:

- два независимых пользователя;
- семью owner/member и отдельную вторую семью;
- Free, Plus, Pro и former-Pro состояния;
- администратора и модератора;
- рецепты private, pending и public;
- партии, планы, списки, дневник, подписку, уведомления и обращения.

Для каждого семейного/пользовательского объекта проверьте положительный доступ владельца и отрицательный доступ другой семьи. Попытка подставить чужой UUID не должна раскрывать ни существование, ни содержимое записи сверх контрактного ответа.

## 8. Конкурентность и идемпотентность

1. Два параллельных update с одной base version: выигрывает один; второй получает conflict/precondition failure.
2. Повтор команды с тем же idempotency key возвращает тот же результат без второй записи эффекта.
3. Тот же key с другим payload отклоняется.
4. Две попытки принять одно приглашение, использовать recovery-код, завершить MFA или списать квоту дают одного победителя.
5. Параллельные движения запасов не создают отрицательное количество.
6. Параллельные изменения плана/заметки/notification settings сериализуются или возвращают явный конфликт.
7. После неизвестного сетевого исхода readback доказывает ноль или один эффект.

## 9. Доменные инварианты

### Аккаунт и сессии

- Нормализованный логин/email уникален.
- Logout/revoke делают сессию недействительной сразу.
- Удаление аккаунта блокируется до готового экспорта и одобренного review.
- Soft/deleted/blocked записи не возвращаются обычным пользовательским запросом.

### Семья и права

- В семье ровно один действующий owner.
- Передача владения атомарна.
- Удаление/блокировка владельца не оставляет dangling family ownership.
- Семейное Plus-покрытие вычисляется из действующих периодов, а не копируется навсегда.

### Запасы, рецепты и планирование

- Единицы/конверсии совместимы; округление не создаёт скрытой отрицательной массы.
- Consumption и correction имеют историю движений.
- Public recipe указывает только на одобренную revision; `recipe_publications.recipe_id` совпадает с revision, active publication ровно одна на recipe, а compatibility-trigger принимает старую вставку без `recipe_id`.
- Recipe moderation case уникален для revision; `kind='recipe'` без revision отклоняется. Upgrade v28→v29 backfill и preflight rollback на несовместимых дублях проверяются отдельно.
- Pending/rejected revision не уничтожает последнюю public revision.
- План, покупки и партии изолированы семьёй.

### Подписки и деньги

- Периоды не дают необоснованное двойное покрытие.
- Freeze сдвигает expiry только на фактическую длительность.
- Refund без provider confirmation не меняет ledger.
- Minor units сохраняются точно, включая ноль и большие допустимые значения.

### Коммуникации и модерация

- Public reply отделён от private note.
- Notification acknowledgement идемпотентен.
- Audit append-only и не содержит секретов.
- Санкция/апелляция изменяет только целевую запись.

## 10. Производительность и эксплуатационные запросы

Соберите `EXPLAIN (ANALYZE, BUFFERS)` на объёмах, близких к production-like:

- cursor pagination списков;
- home/overview агрегаты;
- поиск каталога и дедупликация;
- inventory batches и expiry;
- recipe/community feed;
- admin audit/jobs/incidents;
- nutrition analytics и billing/quota readback.

Критерии: нет незапланированного полного scan крупной таблицы, сортировки не уходят в чрезмерный temp, cursor использует устойчивый индекс, запрос ограничен tenant/family predicate. Зафиксируйте p50/p95/p99 на сервере, а не только единичный локальный результат.

Дополнительно во время 30-минутного backend soak проверяйте `pg_stat_activity`, ожидания/долгие транзакции, temp bytes, dead tuples, рост WAL и pool waiters. После очистки тестовых данных выполните `ANALYZE` затронутых таблиц и убедитесь, что нет оставшихся idle-in-transaction sessions, advisory locks и временных объектов. Автоматический `VACUUM FULL` в работающем контуре не выполнять: необходимость обслуживания оценивается отдельно по bloat и доступному maintenance window.

## 11. Backup и restore drill

1. Создайте изолированную target-БД, не связанную с работающим приложением.
2. Восстановите custom-format backup.
3. Выполните миграционный plan, структурные проверки, baseline-счётчики и выборочные доменные readback.
4. Запустите backend smoke против восстановленной БД runtime-ролью.
5. Зафиксируйте длительность backup/restore и сравните с RPO/RTO.

Никогда не считайте backup проверенным без успешного restore в отдельную БД.

## 12. Очистка после теста

Перед очисткой зафиксируйте количество тестовых строк по namespace и убедитесь, что оно не включает системные справочники. Предпочтительный способ — восстановление заранее снятого baseline после отдельного подтверждения destructive-операции. Альтернатива — проверенный cleanup-скрипт с точными predicates и readback.

После очистки подтвердите:

- доменные таблицы вернулись к baseline-счётчикам;
- сохранились 30 migration rows и канонические справочники;
- нет тестовых ролей, активных подключений и временных БД;
- checksum/размер baseline совпадают;
- `db:plan` снова чист;
- config/log checks не показывают ошибок.

## 13. Текущий известный production gate

На тестовом VPS структурный baseline и локальные backup-файлы проверены; UFW активен и разрешает только OpenSSH и `Nginx Full`. Однако автоматическая/off-host backup-политика и план установки OS security updates с согласованным reboot window должны быть закрыты до публичного production-запуска. На VPS настроен swap, но это не заменяет capacity evidence: перед совместным размещением PostgreSQL, API и OCR/image workers нужен отдельный capacity/oom drill, лимиты worker-процессов и обоснованный предел соединений (кластер сейчас допускает 100). Эти инфраструктурные пункты нельзя считать исправленными тестами приложения.
