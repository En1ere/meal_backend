# Качество, безопасность и инфраструктура

## Уточнение 3.32 — база, время и документация, 25 сентября 2026

База PostgreSQL называется `meal_planner_postgres`; текущая разработка ведётся на Windows, будущий сервер — Linux. Сначала согласуется граф данных, после него — реализация схемы. Документация ведётся параллельно для человека и для агентов, сохраняется в репозитории вместе с версионированной структурой.

Моменты событий нормализуются в UTC, клиент отображает локальное время пользователя. Для календарных правил подписки и AI-квоты применяется явно зафиксированное московское время сервиса (`Europe/Moscow`). Календарные даты без времени, например день плана или срок годности, сохраняют значение даты и не переводятся между поясами. Личные расписания используют свой часовой пояс; источник серверного времени не подменяется часами клиента.

Часть спецификации **3.32.1**. [Master и приоритет правил](../../MEAL_PLANNER_MASTER_v3.md). Номера исходных разделов сохранены; уточнения §28 имеют прежний приоритет. История макетов и состояние реализации перенесены в архив.

<a id="251-данные-и-надёжность"></a>

## 25.1. Данные и надёжность

<!-- /migration:source-2109 -->

<a id="source-2111"></a>
<!-- migration:source-2111 -->

- Не терять локальные пользовательские изменения.
- Все очереди синхронизации должны иметь статус, попытки повтора и идемпотентность.
- Чувствительные локальные данные минимизируются и защищаются по утверждённой threat model; перечень полей и уровни encryption in transit, at rest и field-level фиксируются в технической спецификации. Расплывчатое «частичное шифрование» не считается критерием готовности.
- Критичные модерационные действия и движения запасов должны иметь аудит.

<a id="252-ux"></a>

## 25.2. UX

<!-- /migration:source-2116 -->

<a id="source-2118"></a>
<!-- migration:source-2118 -->

- Обычные пользовательские экраны используют ясный разговорный язык и объясняют действие через понятный результат. Официально-деловые и юридические формулировки допускаются только внутри соглашений, политик, условий, обязательных предупреждений и других соответствующих документов; навигация, заголовки, кнопки и обычные подсказки не должны без необходимости использовать внутренние термины или канцелярит.
- Интерфейс должен сообщать о приблизительности стоимости.
- Стоимостная плашка должна быть консистентна на всех экранах.
- Пользователь должен понимать, что происходит в офлайне и когда данные синхронизируются.
- Таймеры должны быть читаемыми одной рукой и не мешать готовке.
- Ночные уведомления отключены по умолчанию в тихие часы.

## 25.3. Право и безопасность

<!-- /migration:source-2125 -->

<a id="source-2127"></a>
<!-- migration:source-2127 -->

- До публичного запуска провести юридическую проверку политики обработки персональных данных и пользовательских условий для РФ.
- До публичного запуска определить поставщика объектного хранения, резервное копирование, регионы размещения данных и правила удаления.
- Все автоматические модерационные решения должны оставлять возможность ручной проверки и апелляции.
- До реализации детских профилей определить guardian consent, доступ членов семьи, экспорт, исправление и удаление возрастных, аллергических и иных чувствительных данных ребёнка.

## 28.13. Инфраструктура и эксплуатация

<!-- /migration:source-2313 -->

<a id="source-2315"></a>
<!-- migration:source-2315 -->

Подтверждённые исходные условия: Linux-сервер Aeza (ресурсы/регион позже), GitHub, разработка Windows/IDEA, Node.js + NestJS + TypeScript backend (новый проект back), PostgreSQL как база, отдельного QA нет — владелец и AI с автоматическими тестами. Широкая браузерная поддержка превращается в явную матрицу.
<!-- /migration:source-2315 -->

<a id="source-2317"></a>
<!-- migration:source-2317 -->

Рекомендуемая, но ещё не утверждённая схема: один VPS, Docker Compose, Caddy, модульный монолит с отдельными API/worker, PostgreSQL и постоянным файловым хранилищем; pg-boss как кандидат очереди. Local/test/prod разделены по данным и секретам; CI собирает Linux-образ, тестирует, развёртывает test и требует ручного production-подтверждения. Миграции обратно совместимы; rollback приложения не равен восстановлению БД.
<!-- /migration:source-2317 -->

<a id="source-2319"></a>
<!-- migration:source-2319 -->

Бэкап зашифрован вне Aeza, дополнительная копия может забираться на ПК; сохранять БД, файлы и настройки, регулярно проверять восстановление. Внешний uptime-контроль сообщает вне админки, потому что упавший backend не уведомит сам. Секреты вне Git/frontend/образов, разные для окружений, AI-ключ только backend. Открыты: поставщики, серверные ресурсы, домен, бюджет, RPO/RTO, retention, нагрузка и точная browser matrix.
