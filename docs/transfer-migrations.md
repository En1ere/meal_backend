# Развёртывание PostgreSQL

Самостоятельный backend содержит полную схему PostgreSQL 18: `database/migrations/001`–`028`, manifest с SHA256 и application grants. Дамп и старый общий репозиторий для чистой установки не нужны. Runtime PostgreSQL, секреты, реальные данные и старые тестовые аккаунты не переносятся.

API подключается только к `meal_planner_postgres` через ограниченную роль `meal_app` (NOINHERIT, NOSUPERUSER, NOCREATEDB, NOCREATEROLE, NOREPLICATION, NOBYPASSRLS). Владелец БД и миграций — `alex`; приложение не использует owner.

1. Проверить целевой хост, ОС, свободное место, существующие кластеры и данные. Никогда не перезаписывать существующую БД.
2. Установить PostgreSQL 18. Оставить `listen_addresses=localhost`; публичный порт 5432 не открывать.
3. Создать владельца и пустую БД `meal_planner_postgres`, затем ограниченную роль `meal_app`. Пароли передавать защищённо, без Git и истории команд.
4. Выполнить `npm run db:plan` и проверить manifest. Применить `npm run db:migrate -- --environment=test` с PGHOST/PGPORT/PGDATABASE/PGUSER и защищённым PGPASSFILE только в согласованном окружении. Runner проверяет major 18, окружение и SHA256 и применяет миграции в одной транзакции.
5. Выдать `CONNECT` на БД и `USAGE` на `meal` роли `meal_app`, затем отдельно применить `database/application-grants.sql` от владельца.
6. От владельца явно применить `database/reference-data.sql`: ровно 7 units и 3 billing_products. UUID создаются как в исходном seed; backend находит записи по code, фиксированные UUID не требуются. Существующие строки не перезаписываются; несовпадение канонических значений откатывает всю транзакцию. Повторное применение сохраняет UUID.
7. Проверить 29 записей истории, 209 таблиц, 483 внешних ключа, ownership и ограничения runtime-роли. Выполнить backup и проверку restore в отдельной тестовой БД до production.
8. Для локальной разработки открыть SSH tunnel: `ssh -N -L 15432:127.0.0.1:5432 alex@91.201.42.153`. `DATABASE_URL` приложения направить на `127.0.0.1:15432/meal_planner_postgres` с ролью `meal_app`.
9. Запустить API и проверить `/health/live`, `/health/ready`; затем независимый Next.js клиент из `meal_frontend` и Vite админку из `meal_admin`, каждый с `BACKEND_ORIGIN=http://127.0.0.1:3001`; админка использует `VITE_API_MODE=real`. Клиент работает на origin `http://localhost:3000`, админка — на `http://localhost:3002`.

Миграции и seed не запускаются автоматически при `npm start`. Внешние workers оставлять отключёнными до отдельного согласования. Чистая установка не создаёт пользователей приложения; reference-data.sql отдельно создаёт канонические единицы и тарифные продукты без цен, подписок и платёжных эффектов. Изолированный acceptance runner создаёт собственные fixtures, но не используется на общей серверной БД.

Тестовая цель пользователя: Ubuntu 24.04, `91.201.42.153`, технический домен `abstract-usable-gazebo.ruweb.place`. На VPS развёрнуты backend, frontend и admin; актуальный inventory, health-check и rollback описаны в `docs/DEPLOYMENT.md`. Этот документ остаётся инструкцией чистого переноса PostgreSQL, а не журналом application release. Пароли не входят в репозиторий. Rollback новой установки — остановить использование новой БД и сохранить её backup; удаление данных и системных пользователей требует отдельного решения.

## Проверенное тестовое развёртывание — 24.10.2026

На указанном VPS установлен PostgreSQL 18.6, кластер `18/main`, порт 5432 только на `127.0.0.1`/`::1`. Создан серверный `alex` с sudo и PostgreSQL `alex` как владелец новой БД и схемы. `meal_app` имеет ограниченные grants и не имеет CREATE на схему, DELETE пользователей, role-management или SUPERUSER/BYPASSRLS/INHERIT/REPLICATION.

Применены 28 миграций, проверены SHA256 истории, 209 таблиц и 482 внешних ключа. Backend через SSH tunnel на локальный 15432 возвращает readiness 200. Проверена транзакционная запись/чтение тестового пользователя и ROLLBACK с отсутствием записи после отката; запрещённые DDL/DELETE отклоняются с 42501. Схема исходно не использует PostgreSQL RLS (0 таблиц с relrowsecurity); доступ ограничивается grants и серверными проверками авторизации.

Первичный backup: `/var/backups/meal-planner/initial-v28.dump`, 2 109 490 байт, mode 600, доступ root. Backup фактически восстановлен через `pg_restore --exit-on-error` в отдельную временную БД `meal_split_restore_check_20261024`: проверены 28 миграций и SHA, 209 таблиц, 482 FK, отсутствие unvalidated constraints и пользователей. Проверочная БД удалена после успешной проверки; рабочая тестовая БД сохранена. Миграции не создают старые пользовательские данные. Локальный `.env` с новой runtime-ролью игнорируется Git и защищён ACL; секреты отсутствуют в документации и версиях.

После явного `reference-data.sql` проверены 7 канонических единиц и 3 тарифных продукта. Повторное применение сохранило UUID и значения; аккаунтов по-прежнему 0. Актуальный backup с этими справочниками — `/var/backups/meal-planner/baseline-v28.dump`, 2 109 913 байт, mode 600. Он также фактически восстановлен в изолированную БД: подтверждены 28 миграций, 209 таблиц, 482 FK, 0 unvalidated constraints, 0 пользователей, 7 единиц и 3 тарифных продукта, SHA истории совпали. Проверочная БД удалена.
